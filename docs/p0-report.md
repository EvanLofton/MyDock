# Dock 项目 P0 可行性验证报告

| 项目 | 内容 |
|---|---|
| 验证目标 | 把 P0 的三个未知项变成确定项，并据此定下毛玻璃路线 |
| 验证日期 | 本次会话 |
| 验证方式 | 纯 Rust + Win32 探针（`probe/`），**全自动化像素/焦点/时序判定**，不依赖肉眼观察 |
| 结论 | **三项全部通过，方案可行。路线定为 A（官方 DWM 系统背景）。发现 3 个必须在 P1 处理的新约束。** |

## 0. 摘要

| 问题 | 结论 |
|---|---|
| 毛玻璃能不能做？ | ✅ **能**，模糊半径约 **76 px**，强度足够，观感接近 macOS |
| 哪条路线？ | ✅ **路线 A**：`DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_TRANSIENTWINDOW` |

## 2. T1 毛玻璃

### 2.1 方法

在待测窗口**背后**放一块已知图案的背景窗，抓取覆盖区域的屏幕像素，用统计量反推模糊是否发生。

背景窗最先创建并设为 `TOPMOST`，待测玻璃窗后创建（同为 `TOPMOST`），保证玻璃窗一定叠在背景之上。

测试矩阵：**5 条路线 × 3 种窗口样式 × 3 种焦点状态**。

### 2.2 第一次尝试失败（记录在案）

第一版用 **8 px 黑白棋盘格**作背景，结论是"所有路线都没有产生模糊"。

**这个结论是错的，错在测试设计**：亚克力的实际模糊半径约 76 px，远大于 8 px 的格子，整片图案被完全平均掉，表现为"均匀色块"。据此无法区分"真模糊"与"不透明色罩"。

旁证：同一配置在两次运行中给出 **211.0** 与 **181.0** 两个不同的平坦值——如果是不透明固定色不可能变化，说明它**确实在与背后内容合成**。

### 2.3 修正后的方法：锐利边缘法（T1c）

改用**左黑右白的单条锐利竖直边缘**作背景，直接测量 10%→90% 的**过渡宽度（像素）**：

- 无模糊 → 过渡宽度 ≈ 1–2 px，对比度 ≈ 255
- 有模糊 → 过渡宽度显著变大，对比度下降

这个指标无歧义，且能定量给出模糊强度。

### 2.4 结果

基线（无玻璃窗）：**过渡宽度 1.0 px，对比度 255**

| 路线 | 样式 | 过渡宽度 | 对比度 | 判定 |
|---|---|---|---|---|
| 对照：完全透明窗 | 全部 3 种 | 1.0 px | 255 | 未受影响（**对照组有效**） |
| 对照：不透明红 | plain | — | 0 | 纯色（**对照组有效**） |
| **A-acrylic** | plain | **76.0 px** | 92 | **真·强模糊** |
| **A-acrylic** | noredir | **76.0 px** | 92 | **真·强模糊** |
| **A-acrylic** | layered | **66.0 px** | 111 | **真·强模糊** |
| **B-acrylic** | plain / noredir | **82.0 px** | 62 | **真·强模糊** |
| **B-acrylic** | layered | **62.0 px** | 84 | **真·强模糊** |
| A-mica | plain / noredir | — | ~1 | 不透明（Mica 只模糊壁纸，不模糊窗口） |

三种焦点状态（**focused / unfocused / noactivate**）在**每一行都给出完全相同的数值**。

### 2.5 结论

1. **路线 A 与路线 B 都能产生真实、强烈的模糊**，过渡宽度 62–82 px。
2. **`DWMSBT_TRANSIENTWINDOW`（路线 A）优于路线 B**：同样的模糊强度下对比度更高（92 vs 62），即对背后内容的亮度保留更好、着色更轻，更接近 macOS 的通透观感。且它是**官方 API**，不是未公开接口。
3. **`WS_EX_NOREDIRECTIONBITMAP`（Tauri/tao 透明窗口所用样式）下路线 A 表现与 plain 完全一致**（76.0 / 92）——这对 Tauri 方案是极好的消息。
4. **`WS_EX_LAYERED` 会略微削弱效果**（76→66 px），因为 225/255 的 alpha 会把一层**未模糊**的内容叠上来。**结论：Dock 主窗口不要用 `WS_EX_LAYERED`。**
5. **Mica（`DWMSBT_MAINWINDOW`）不可用**：对比度 ≈ 1，等于完全不透。与社区经验一致——Mica 模糊的是壁纸，不是窗口背后的内容。
6. ❗ **「窗口失焦后 acrylic 模糊失效」的说法在本机完全没有复现。** 失焦态与 `WS_EX_NOACTIVATE`（永不获得焦点）态下，模糊强度与获得焦点时**完全一致**。

> 第 6 条是本次 P0 最有价值的结论之一。它推翻了 [Tauri #12854](https://github.com/tauri-apps/tauri/issues/12854) 与多篇实践文章里"必须在失焦时切换为不透明背景"的变通做法。**Dock 作为永远失焦的窗口，可以稳定保有毛玻璃。**
>
> 保守起见，P1 仍会在**真实 Tauri 窗口**里复验一次（探针用的是裸 Win32 窗口）。

### 2.6 实现要点（实测踩坑，P1 必须遵守）

| # | 要点 | 说明 |
|---|---|---|
| 1 | **`SetWindowCompositionAttribute` 必须动态取地址** | 它是 `user32.dll` 的导出（序号 2391），但**不在 Windows SDK 的 `user32.lib` 导入库里**，静态链接直接 `LNK2019`。必须 `LoadLibraryA` + `GetProcAddress`（`window-vibrancy` 亦如此）。仅在走路线 B 兜底时需要 |
| 2 | **acrylic 的 `AccentFlags` 必须为 0** | 非 0（如 `BLURBEHIND` 用的 2）行为不正确 |
| 3 | **acrylic 的 alpha 不能为 0** | 传 0 会失效，需钳到 1 |
| 4 | **`GradientColor` 打包格式为 `0xAABBGGRR`** | 低字节是 R，不是 A |
| 5 | **窗口不要用 `WS_EX_LAYERED`** | 会叠加一层未模糊内容，削弱效果 |

## 3. T2：点击 Dock 是否夺走当前应用焦点

### 3.1 方法

先用真实点击把焦点交给目标窗口，再用 `SendInput` 真实点击 Dock 窗口，比对 `GetForegroundWindow()` 是否变化。同时统计 Dock 窗口**是否真的收到了点击**（`WM_LBUTTONDOWN` 计数），以区分"没抢焦点"和"点击压根没送达"。

对照组（不做任何保护）必须被夺焦点，否则说明测试无效。

### 3.2 结果

**跨进程（焦点目标是另一个进程，即 Dock 的真实工况）**

| 变体 | 结果 |
|---|---|
| `WS_EX_NOACTIVATE` 单独 | ✅ **焦点未被夺** |
| `WS_EX_NOACTIVATE` + `WM_MOUSEACTIVATE → MA_NOACTIVATE` | ✅ 焦点未被夺 |
| 对照：无任何保护 | ❌ 焦点被夺（**对照组有效**） |

**同进程（焦点目标与 Dock 属于同一进程）**

| 变体 | 结果 |
|---|---|
| `WS_EX_NOACTIVATE` 单独 | ❌ **焦点仍被夺走** |
| `WS_EX_NOACTIVATE` + `MA_NOACTIVATE` | ✅ 焦点未被夺 |
| **仅 `MA_NOACTIVATE`**（不设 `WS_EX_NOACTIVATE`） | ✅ 焦点未被夺 |
| 对照：无任何保护 | ❌ 焦点被夺（**对照组有效**） |

已回读 `GWL_EXSTYLE` 确认 `WS_EX_NOACTIVATE` **确实已生效**（`exNOACT=true`），排除"样式没设上"的可能。

### 3.3 结论

> **微软文档是对的，但只在跨进程时成立。`WS_EX_NOACTIVATE` 对同一进程的窗口不起作用**——同进程的窗口之间仍可互相激活。真正起作用的是 `WM_MOUSEACTIVATE` 返回 `MA_NOACTIVATE`。

**对 Dock 的要求**：

- 跨进程（Dock 被点击时前台是别的应用）→ `WS_EX_NOACTIVATE` 已足够；
- **但同进程场景必须覆盖**：右键菜单弹窗、设置窗口、托盘菜单打开时用户又点了 Dock 本体；
- ⇒ **两个都做**：`WS_EX_NOACTIVATE` + `WM_MOUSEACTIVATE → MA_NOACTIVATE`。代价近乎为零，且能覆盖全部场景。

### 3.4 ❗对 P1 的直接影响（新增实现风险）

**Tauri/tao 没有暴露 `WM_MOUSEACTIVATE` 的处理入口。** 在真实 Tauri 窗口中实现该 handler，需要：

1. 首选：用 `SetWindowSubclass` 对 Tauri 窗口的 HWND 做子类化，拦截 `WM_MOUSEACTIVATE`；
2. 备选：`SetWindowsHookEx(WH_CALLWNDPROC)`；
3. 先验证：**tao 在设置 `WS_EX_NOACTIVATE` 时可能已经自行处理了该消息**。

⇒ **P1 的第一件事应该是：在真实 Tauri 窗口上复跑本 T2 探针，确认是否还需要额外子类化。**

## 4. T3：双窗口自动隐藏的帧率

### 4.1 方法

创建触发条窗口（贴底 3 px）与 Dock 窗口（900×90），以三角波在"显示位置 ↔ 隐藏位置"之间移动 Dock 窗口 900 帧，记录每次 `SetWindowPos` 的耗时，并对比**无玻璃 / 路线 A / 路线 B** 三种状态。

### 4.2 结果

60 Hz，帧预算 **16667 µs**。

**未限速：单次 `SetWindowPos` 原始耗时（µs）**

| 毛玻璃 | avg | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| 无 | 317.3 | 200.1 | 590.9 | 912.1 | 2072.1 |
| 路线 A (acrylic) | **313.3** | 204.5 | 605.7 | 778.0 | 1069.8 |
| 路线 B (acrylic) | **311.7** | 181.9 | 577.6 | 744.0 | 1089.4 |

**限速对齐 60 Hz：每帧迟到量（µs）**

| 毛玻璃 | avg | p95 | max |
|---|---|---|---|
| 无 | 481.5 | 942.7 | 1374.3 |
| 路线 A | 437.5 | 810.8 | 1411.5 |
| 路线 B | 460.3 | 933.5 | 1324.6 |

### 4.3 结论

1. **亚克力对窗口移动的额外开销在噪声范围内测不出来**：313 µs（A）vs 317 µs（无玻璃）。
2. **最坏情况占 60 Hz 帧预算的 12.4%**（2072 µs / 16667 µs）。即便按 120 Hz 的 8333 µs 预算，余量仍有 **4 倍以上**。
3. **风险 R5（亚克力 + 高频窗口移动导致掉帧）销案。** 双窗口设计（隐藏时仅移动约 80 px）在实测下是安全的。
4. 「无玻璃」组的 max 反而最高（2072 µs），因为它是第一轮、窗口刚创建、缓存冷。这进一步说明差异来自噪声而非亚克力。

> 限制：本机为 60 Hz，**未能在 120 Hz 上直接实测**。结论依据是"单次调用耗时远低于 120 Hz 帧预算"，属于推断而非直测，P2 换高刷屏后应复测。

## 5. 其他实测发现

| # | 发现 | 影响 |
|---|---|---|
| 1 | **`WS_EX_NOREDIRECTIONBITMAP` 窗口完全不渲染 GDI 绘制内容** | T1 中"不透明红"对照在该样式下测出对比度 255（= 什么都没画）。**P1 若用此样式，绝不能用 GDI 绘制 Dock 内容**；对 Tauri/WebView2 无影响（内容由 WebView 合成） |
| 2 | **DWM 系统材质在浅色主题下是不透明的浅色**（mean ≈ 181） | 路线 A 自带浅色材质底。要做深色 Dock，需在其上叠 CSS 深色半透明层（**OS 模糊 + CSS 染色**混合方案），或试 `DWMWA_USE_IMMERSIVE_DARK_MODE` |
| 3 | **`SetForegroundWindow` 在后台进程中会被静默忽略** | 探针第一版因此得出错误结论。必须用 `AttachThreadInput` 先附加到前台线程。**这条同样是 P1「点击切换应用」的核心技术，风险 R2 的应对方案得到实测验证** |
| 4 | **任务栏为自动隐藏（工作区 = 全屏）** | 见 §6 |
