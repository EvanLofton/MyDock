## 已完成的优化（不在待办里，仅记录）

**2026-09：`reveal.rs` 主循环的无条件 `SetWindowPos`**（BL-2 的副产物）

这是本项目**最大的一处纯浪费**：自动隐藏主循环是 62.5 Hz（`sleep(16ms)`），
而两条分支都**无条件**调用 `move_to`（= `SetWindowPos`），单次带亚克力的移动实测
**~313 µs**，于是 `62.5 × 313µs ≈ 1.96% 单核` 被永久浪费在
「把窗口挪到它已经在的地方」。

修复：`reveal.rs` 新增 `Applied` 结构 + `move_if_changed()`，矩形没变就跳过。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 空闲 CPU（自动隐藏开） | 2.34% 单核 | **0.42 ~ 0.47% 单核** |
| 自动隐藏行为 | — | 不变（实测：鼠标离开 y=866，触底 y=744） |

**教训**：`SetWindowPos` 这类「重设窗口状态」的调用**不是免费的**（会让 DWM 重新合成），
放进高频循环前必须先判断「真的变了吗」。

## BL-1 用 SetWinEventHook 事件推送替换轮询

**状态：待办。动机已修正。有一条未验证的前置条件。**

> ### ⚠️ 动机已修正（2026-09，BL-2 实测后）
>
> 本条目**原来**的动机是「轮询导致空闲 CPU 2.1% 单核」。**这个论证是错的。**
>
> 实测：把前端轮询间隔从 1.5 秒改成 **60 秒**（几乎不轮询），空闲 CPU 只从
> 2.34% 降到 **2.188%** —— **整条轮询链路只占 0.15% 单核**。
> 那 2.1% 的真正来源是 `reveal.rs` 的无条件 `SetWindowPos`，已单独修复（见上）。
>
> 所以：**BL-1 不再有 CPU 理由。** 它只剩下「亚秒级延迟」和「为后续特性铺路」
> 这两条（见「会咬到后续开发的地方」）。将来重新评估时如果忘了这一点，
> 就会为了 0.15% 去做一次风险不小的改造。

### 动机（修正后）

Dock 需要知道「某个应用的窗口出现了 / 消失了 / 最小化了 / 抢到前台了」，才能正确画
运行指示点（白点）。当前实现是前端**定时轮询**。

轮询剩下的唯一代价是**延迟下限**：不是自己触发的状态变化，最坏要等一个轮询周期
（空闲 1.5 秒）才看到。CPU 代价经实测已可忽略（0.15% 单核）。

### 为什么现在这样写（前因）

原本是固定 4 秒盲轮询，用户实测「点图标启动程序后白点 2~4 秒才出现」。
2026-09 改成自适应轮询：

- 空闲 `POLL_IDLE_MS = 1500` —— 只为兜住**不是我们触发的**变化（例如从任务栏关程序）
- 变化后 / 点图标后 `POLL_FAST_MS = 250` 连打 14 轮（≈3.5 秒，够等程序建出窗口）

**关键设计点**：「点图标」是**本地已知事件**（`onActivate` 里直接调 `kickPoll.current()`），
没必要靠盲轮询去发现它。所以用户自己的操作响应很快；慢的只剩外部触发的变化。

用户反馈「白点响应速度已经够快了」—— 延迟问题在当前使用范围内**已经解决**。

### 为什么这不是最优解

轮询是把「我不知道什么时候会变」换成「我定期去问」。事件钩子是让系统在变的时候**告诉我**。

`SetWinEventHook` 是 Windows 为这件事提供的正规机制，而且**设计文档里早就规划好了** ——
实现时应当遵循它，不要重新发明参数：

| 出处 | 已定的内容 |
|---|---|
| `dock-technical-design.md` §3.3 | 「**窗口枚举的频率：不要轮询**」；用 `EVENT_OBJECT_CREATE/DESTROY/SHOW/HIDE`，`WINEVENT_OUTOFCONTEXT`，**事件后 300 ms 防抖**再重新枚举 |
| `dock-technical-design.md`（事件表） | 事件名 `dock://apps-changed`，载荷 `DockApp[]` + 运行态 |
| `dock-technical-design.md`（模块图） | 模块名 `events.rs` |
| `dock-technical-design.md` P2 列表 | 「`SetWinEventHook` 自动发现运行窗口，替换轮询」 |

所以本条目不是新提议，而是**把设计文档里已规划、当时因工期跳过的部分补上**。
下面方案里的参数（300 ms 防抖、模块名 `events.rs`、事件名）都与设计文档对齐；
只有 `EVENT_SYSTEM_FOREGROUND` 和 `EVENT_SYSTEM_MINIMIZESTART/END` 是本条目补充的 ——
设计文档只列了 `OBJECT_*` 四个，但白点还依赖前台与最小化状态。

### 会咬到后续开发的地方

**1. 任何要求亚秒级反应的特性都会撞到 1.5 秒这堵墙**

- 悬停**窗口预览缩略图**（需要实时窗口列表和尺寸）
- **每个窗口一个白点**（而不是每个应用一个，macOS 是这样）
- 图标下显示**当前窗口标题**
- **独占全屏时抑制自动隐藏**（需要立刻知道前台是谁）

**2. 状态指纹是个手工维护的隐式契约 —— 最现实的摩擦**

```js
// App.tsx
const sig = apps
  .map((a) => `${a.id}|${a.running ? 1 : 0}|${a.hasForeground ? 1 : 0}|${a.windows.length}`)
  .sort()
  .join(",");
```

`DockVisualItem` 有 11 个字段，指纹只覆盖了 4 个。以后每加一个与「变化」有关的字段，
都要**记得**同步改这里，否则它会悄悄退化成 1.5 秒。现有例子：`hwnd` 就不在指纹里 ——
同一个应用换了个窗口（窗口数不变）不会触发快节奏。

**不会显示错**：`load()` 每轮都无条件 `setItems(built)`，指纹只决定**下一轮多久之后再查**。
所以漏判的后果是「慢」，不是「错」。这一点让风险可控，但也意味着**它不会报错**，
只能靠人记住。

**3. 与「连续运行 8 小时不崩」的验收标准有交互**

空闲每 1.5 秒唤醒意味着进程**永不进入深睡眠**（台机无所谓，笔记本上电池差异可测）。
另外枚举路径里有 COM 调用（`window_aumid` 每次 `SHGetPropertyStoreForWindow` +
`CoTaskMemFree`），长跑下任何一处漏释放都会更快暴露。**这条没有实测数据，只是风险方向。**

### 影响面：好消息

这个取舍**只影响「怎么知道状态变了」这一件事**。下面这些**完全不依赖**它：

- `pinned` 列表与身份模型（`apps.rs::enumerate_dock_apps`）
- 窗口层：毛玻璃（`glass.rs`）、焦点防护（`win_layer.rs`）、自动隐藏（`reveal.rs`）
- 点击行为、右键菜单、启动、图标提取

所以要替换的只有三处：

| 现在 | 改成 |
|---|---|
| 轮询 effect 里的 `setTimeout(tick, …)` | `listen("dock://apps-changed", load)` |
| `kickPoll.current()`（4 处调用） | 不需要了（Rust 会推） |
| 无 | 新增 `events.rs` + 一个 Tauri capability |

**这是一次可以随时做的替换，不是欠债。**

### 触发条件

满足任意一条就做，不要凭感觉：

- 要做上面「第 1 条」里的任何一个特性
- 要给 `DockVisualItem` 加字段（顺手把指纹删掉，别再维护它）
- 从别处关掉程序时，1.5 秒延迟被用户抱怨
- 8 小时长稳里观察到内存/句柄缓慢增长，怀疑枚举路径泄漏

> ❌ 「空闲 CPU 高」**不再**是触发条件（实测轮询只占 0.15%，见上方红框）。

### 实施方案

**1. 新增 `app/src-tauri/src/events.rs`**（模块名沿用设计文档模块图里的 `events.rs`）

- 起一条**专用线程**，自己 `GetMessageW` 泵消息。原因：`SetWinEventHook` 的回调
  投递到**安装钩子的那个线程**的消息队列（和 `SetWindowSubclass` 一样是线程局部的 ——
  这个项目已经在子类化上踩过一次，别再踩）。
- `SetWinEventHook` 参数：`WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS`
  （与设计文档 §3.3 一致）。`OUTOFCONTEXT` 表示不需要注入别的进程。
- 关心的事件：

  | 事件 | 用途 | 来源 |
  |---|---|---|
  | `EVENT_OBJECT_SHOW` / `EVENT_OBJECT_HIDE` | 窗口出现 / 消失 → 白点开关 | 设计文档 §3.3 |
  | `EVENT_OBJECT_CREATE` / `EVENT_OBJECT_DESTROY` | 应用启动 / 退出 | 设计文档 §3.3 |
  | `EVENT_SYSTEM_FOREGROUND` | 前台切换 → `has_foreground` | 本条目补充 |
  | `EVENT_SYSTEM_MINIMIZESTART` / `MINIMIZEEND` | 最小化状态变化 | 本条目补充 |

- 回调里**只做一件事**：给 channel 发一个空消息。绝不在回调里枚举或加锁
  （回调在消息泵线程上跑，阻塞它会拖住整个钩子）。
- 主循环做**防抖合并**：收到消息后等 **300 ms**（设计文档 §3.3 定的值），
  把这段时间内的事件合成一次 `enumerate_apps()`，然后
  `app.emit("dock://apps-changed", ...)`。
- 退出时 `UnhookWinEvent` 释放钩子（见「风险与未验证点」）。

**2. 前端 `App.tsx`**

- 用 `listen` 替换 `setTimeout` 循环（`@tauri-apps/api/event`，依赖已存在）。
- **保留一个很慢的兜底轮询**（10~15 秒）。事件可能丢（钩子安装失败、
  某些窗口不产生事件），兜底能自愈，代价可忽略。宁可有一个已知的慢兜底，
  不要假设事件 100% 可靠。
- 删掉状态指纹和 `kickPoll` ref。

**3. 新增 capability**

当前 `app/src-tauri/` 下**没有任何 capability 配置**（`tauri.conf.json` 里没有
`app.security.capabilities`，`capabilities/` 目录也不存在）。而 `listen` 属于 Tauri
核心插件命令，按 v2 的 ACL 需要显式授权。需要新建
`app/src-tauri/capabilities/default.json`：

```json
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "default",
  "description": "Dock 默认能力：前端需要监听 Rust 推送的应用状态变化",
  "windows": ["dock"],
  "permissions": ["core:default"]
}
```

### 风险与未验证点

- ❗**未验证（必须先做）**：Tauri v2 的 capability 是**白名单**语义。当前没有任何
  capability 文件而应用命令能正常工作，说明**应用自身注册的命令不走 ACL**；但加一个
  capability 文件会不会影响现有那 15 个命令（`main.rs` 的 `invoke_handler`），
  **没有验证过**。第一步必须先加空 capability 并跑一遍「点图标启动 / 激活 /
  最小化 / 右键菜单 / 托盘」，确认没有回归，再接事件。
  写错 capability 会把 IPC 整个关掉。
- ❗**未验证**：`SetWinEventHook` 的钩子句柄必须在程序退出时 `UnhookWinEvent`，
  否则长跑下可能积累（对应 8 小时验收）。
- 事件风暴：某些程序（终端、Electron 应用）会产生大量窗口事件。300 ms 去抖可能
  需要按实测调整；另外要考虑「一次事件风暴里最多枚举 N 次」的上限。

### 验收标准

- 白点行为与现在**完全一致**：点图标启动 → 白点出现；关闭 → 消失；
  最小化 → 白点保留且 `最小化=true`
- Dock 上的图标与顺序不变（只由 `pinned` 决定，运行状态不参与）
- 现有 6 项应用操作自检仍 **6/6 通过**（`DOCK_OPSTEST=1`，`--features selftest`）
- 焦点矩阵仍通过：点击 Dock **不夺走**当前应用焦点
- 从别处关掉程序，白点消失延迟 **< 500 ms**（现在是 ≤1.5 秒）
- **空闲 CPU 不得高于 0.5% 单核**（改之前是 0.42 ~ 0.47% —— 别为了 0.15% 的收益
  把这个数搞坏）
- 长稳 8 小时句柄数不增长（含钩子事件句柄）

### 被推翻的「想当然」

记录在这里，因为它们每一个都差点变成一次错误的优化：

| 猜测 | 实测 | 结论 |
|---|---|---|
| 62.5 Hz 自动隐藏循环「读鼠标」是主因 | A/B 对照（自动隐藏开/关）只差 0.23% | ⚠️ 方向对、量级错 —— 真正贵的是循环里的 `SetWindowPos`，不是读鼠标 |
| `EnumWindows` 遍历窗口太多 | 146 个顶层窗口，**131 个被第一个廉价的 `IsWindowVisible` 挡掉**，只有 ≤5 个走到 DWM cloak 查询和跨进程取标题 | ❌ 排除 |
| `window_aumid` 的 COM 调用是主因 | 0.09 ms/轮 | ❌ 排除 |
| 轮询是空闲 CPU 的主因 | 轮询间隔改 60 秒后 CPU 只降 0.15% | ❌ **排除（这条推翻了 BL-1 的原动机）** |

### 两个方法论教训

**1. `DOCK_DEBUG=1` 自身的开销比它测量的对象还大。**
第一轮测量显示「总计 7.7 ms，但已命名段只占 2.5 ms，4.7 ms 不知去向」——
那 4.7 ms 就是 `DOCK_DEBUG` 的打印（把 `DEBUG_PRINT` 单独计时后确认是 5.0 ms）。
**测时间时，被测代码里不能有日志**；无法避免时必须把日志单独计时再减掉。

**2. 不要用「整进程 CPU ÷ 轮询次数」推算单次枚举成本。**
那正是「~30 ms/轮」这个错误数字的来源：`dock-app` 里还有 62.5 Hz 的自动隐藏线程、
3 秒一次的钩子重挂线程、Tauri 运行时 —— 它们全都算进了分子。
**要量哪个函数，就在那个函数里面量。**

### 遗留

- `file_description` 那 1.9 ms 可缓存（exe 路径 → FileDescription 在一次运行内不变），
  见 BL-3。但注意：**轮询总共只占 0.15%，这条的收益上限也就 ~0.1%**，优先级低。
- **计时脚手架已删除**（`timing.rs` 及其在 `apps.rs` / `main.rs` 的 18 处调用点）。
  它是一次性测量工具，量完就该走 —— 产品代码里不留测试脚手架。
  **上面的数字因此不能直接复跑**；要重新量就照下面这样做（约 20 分钟）：

  1. 新建 `apps.rs` 内部的一个 `static` 计时表（`AtomicU64` 存微秒）+ `start()`/`add()`
     两个函数（照抄本文件 BL-2 的表，槽位就是那张表的每一行）；
  2. 在 `enum_cb` 的 `is_cloaked` / `title_of`、以及 `enumerate_apps` 的
     `EnumWindows` / `process_path` / `window_aumid` / `process_aumid` /
     `file_description` / `is_process_elevated` 各处包上计时段；
  3. **`DOCK_DEBUG` 的打印必须单独占一个槽位**，否则会把日志开销算成枚举成本
     （这是第一次测量踩的坑，见下「方法论教训」）；
  4. 每 10 轮打印一次平均值，`DOCK_DEBUG=1` 跑 45 秒即可。

## BL-3 缓存 `file_description()`

**状态：已完成（2026-09）。**

### 落地（2026-09）

`apps::file_description` 加了一层进程内缓存（`OnceLock<Mutex<HashMap<String, Option<String>>>>`，
键是 **小写化的 exe 全路径**）。三个细节：

1. **`None` 也要缓存** —— 读不到版本信息是常态（小工具很多没有），不缓存 `None`
   的话每轮枚举都白读一次版本资源；
2. **键要小写化** —— 不然 `C:\...\Notepad.exe` 和 `c:\...\notepad.exe` 会各读一次
   （而 `id_for_target` 本来就是小写的，说明同一路径的两种写法真的会出现）；
3. **缓存不会失效** —— exe 被就地升级（版本信息变了）不会反映出来。可以接受：
   名字只在**新条目进来**时读一次，用户看到的是列表里存的名字。要更稳得带 mtime，
   但那要点文件时间，收益不成比例。

单测 `apps::tests::file_description_cache_is_consistent` 断言：同一 exe 两次结果一致、
大小写不同命中同一条、不存在的路径两次都是 `None`。

### 动机

`file_description()`（`apps.rs`）读 exe 的 PE 版本资源取 `FileDescription` 当展示名，
实测 **1.9 ms/轮**，占真实枚举成本 2.6 ms 的 **72%**。同一个 exe 每次都重新读文件。

### 现状证据

- 位置：`apps.rs` 的 `file_description()` —— `GetFileVersionInfoSizeW` +
  `GetFileVersionInfoW` + 2× `VerQueryValueW`，都是文件 I/O
- 调用点：`enumerate_apps()` 的 Win32 分支，**每个非打包候选窗口每轮一次**
- BL-2 用（现已删除的）临时计时脚手架测得 **1.88 ~ 1.95 ms/轮**；
  这是 BL-2 那张分段表里唯一值得优化的项（其余各段都 ≤0.3 ms）

### 实施方案

进程内加 `static Mutex<HashMap<String, String>>`（键 = 小写 exe 路径）。
exe 的 FileDescription 在一次运行内不变，无需失效逻辑。

`display_name_for()`（`pub`，别处也在用）走同一个函数，缓存放进 `file_description`
内部即可两边受益。

### 触发条件

- 空闲 CPU 变成关注点（但注意收益上限只有 ~0.1%）
- 或者将来要提高枚举频率（例如为了亚秒级反应而缩短轮询间隔）

### 验收标准

- 展示名不变（对照：仍是「文件资源管理器」「Microsoft Edge」这类应用名，
  不是窗口标题）
- 缓存**确实生效**且不必重建计时脚手架即可验证：把 `file_description` 里的
  `GetFileVersionInfoSizeW` 调用次数记一个 `AtomicU64`，`DOCK_DEBUG=1` 时打印 ——
  改成缓存后，稳态下每轮应该只增加 **0 次**（首次除外）。这比测 ms 更直接、
  也不受计时噪声影响。
- 若确实想量 ms，临时重建计时脚手架（步骤见 BL-2「遗留」），
  `file_description` 应降到 ~0 ms

## BL-4 Dock 内拖拽排序

**状态：已完成（2026-09）**

实现要点与实测结果见本节末尾的「交付结果」。下面保留设计推导，因为里面的两个坑
（`transform` 单写入者、指针捕捉）是花时间才搞清楚的，值得留档。

### 动机

「**Dock 上显示哪些图标、按什么顺序，完全由用户决定**」是 2026-09 定下的模型
（见 `dock-technical-design.md` §4.2「应用顺序模型」）。但顺序目前只能靠
**添加的先后**决定 —— 想调整就只能手工改 `config.json` 里 `pinned` 的顺序。
**没有拖拽排序，这个模型只落地了一半。**

### 现状证据

| 位置 | 说明 |
|---|---|
| `store.rs` 的 `Preferences.pinned` | **这个 Vec 的顺序就是图标的显示顺序**，是唯一真相 |
| `apps.rs::enumerate_dock_apps()` | 一趟遍历 `pinned` 生成显示列表，顺序原样保留 |
| `Dock.tsx` | 按 `items` 顺序渲染；尺寸/位置由 `baseLeft` 决定 |
| `lib/magnify.ts` | 鱼眼放大是 **transform-only**（`translateX + scale`），鼠标位置**绝不进 React state**，靠 rAF 直接写 `el.style.transform` |
| `dock-technical-design.md` 命令表 | 早已规划 `reorder_apps(ids: Vec<String>)`，标注「尚未实现」 |
| 自检 | **没有任何一项覆盖顺序** —— 顺序出问题不会被现有自检发现 |

### 实施方案

**1. Rust**

- `store::reorder(app, ids: &[String]) -> Result<(), String>`：按 `ids` 重排 `pinned`。
  **必须校验 `ids` 与现有 id 集合完全一致**（不重不漏），否则拒绝并返回明确错误 ——
  一个错序的列表会把用户的图标搞丢或搞重复，这种写入不能"尽力而为"。
- 新增命令 `reorder_apps(ids: Vec<String>)`，落盘后 `eval` 通知 Dock 刷新
  （复用 `drop.rs` 里那个 `refresh_apps` 的做法）。

**2. 前端 `Dock.tsx`**

- 用 **pointer 事件**（`pointerdown/move/up` + `setPointerCapture`），不用 HTML5 drag
  —— 后者会与 Tauri 的拖放（从桌面拖进来添加）抢事件。
- ❗**最大的坑：拖拽与鱼眼放大打架。** 放大是每帧用 rAF 直接写
  `transform: translateX(...) scale(...)` 的。拖拽期间必须：
  - 暂停鱼眼（让 `apply(null)` 复位），并让被拖的图标改由拖拽逻辑独占 `transform`；
  - 或者把拖拽位移和放大位移在同一个 `computeLayout` 结果上叠加。**推荐后者**，
    否则鼠标一停一走，transform 会被两个写入者反复覆盖（闪烁）。
- **区分「点击」与「拖动」**：`pointerup` 时若位移小于阈值（约 5px）才当点击放行，
  否则吞掉这次 click —— 否则每次拖完都会启动一个程序。
- 落点 → 用 `baseLeft` 反算插入下标 → 上报新 id 顺序。

**3. 视觉**

拖动中的图标略微放大 + 半透明，其余图标让位（`translateX` 平移）。
`glass.css` 里加一个 `.dock-icon.dragging` 即可。

### 风险与未验证点 —— **已实验澄清**

- ✅ **指针拖出窗口后事件是否还在**：**在**。用 `selftest::drive_drag_probe`
  在真实窗口上合成了一次「按下 → 向上拖 200 逻辑像素 → 抬起」，页面回执：

  ```
  down 298,42 | mv 298,26 | mv 298,10 | mv 298,-7 | … | mv 298,-158 | up 298,-158
  ```

  指针一路到窗口**上方 158 逻辑像素**，`pointermove` 与 `pointerup` **全程送达**，
  没有 `capture-fail`、没有 `cancel`。结论：`setPointerCapture` 在这个
  `WS_EX_NOACTIVATE` 工具窗口里可用，**拖出去删除可行**，而且
  **不需要**拖拽期间加高窗口 —— 也就避开了「透明区域吞掉桌面点击」那个取舍。
- ✅ **拖拽与鱼眼打架**：靠**单写入者**解决 —— `Dock.tsx` 里只有 `apply()` 一个函数写
  `transform`，它按「是否在拖拽」走两条分支；拖拽期间不做鱼眼放大。
  （macOS 拖拽时也是停止放大的观感，但**我无法在这台机器上验证 macOS 的实现**，
  所以这里只把它当作设计约束的旁证，不作为依据。）

### 交付结果

| 需求 | 实现 | 验证 |
|---|---|---|
| 拖拽排序 | pointer 事件 + `setPointerCapture`；每帧算插入槽位，邻居整槽让位（`translateX`） | 自检：`记事本` 从槽 3 拖到槽 6，**落盘顺序正确** ✅ |
| 拖出去 = 删除 | 指针超出面板边缘 26 逻辑像素即进入删除区；松手调 `remove_dock_app` | 自检：`Weixin` 被移除，剩 9 项 ✅ |
| 实时显示正确位置 | 邻居图标每帧整槽平移让位（`slotW * Δ`），被拖图标跟手（含竖直方向） | 排序结果正确即证明槽位计算正确 ✅ |
| **拖出时的反馈** | ① 面板整块描红边 ② 被拖图标淡到 30% ③ **面板顶部显示文字**「松开即移除『应用名』」 ④ 图标跟着光标往上走、被窗口裁掉 | 拖到一半读 DOM：实得 `松开即移除「Weixin」` ✅ |
| 松手不触发启动 | 位移 > 5px 才算拖动；拖动过则 `suppressClickRef` 吞掉随后的 `click` | 自检：被拖的 `记事本`（拖前未运行）拖后仍未运行 ✅ |
| **拖回面板内不误删** | 删除判定看松手那一刻的位置，不看「是否曾经出去过」 | 自检：拖出去再拖回来松手，10 项不变、顺序不变 ✅ |
| 非法顺序保护 | `store::reorder` 要求 id 集合**不重不漏**，否则整条拒绝、一个字节不写 | 自检：少一项时返回错误且列表不变 ✅ |

**文字提示为什么放在面板顶部**：面板只有 **72 逻辑像素**高，而图标占 y=20..64
（44 高、距底 8）——顶部 y=0..20 那条 20px 空白带是**唯一**放得下文字的地方。
也不能用弹窗：弹窗会超出窗口被裁掉（原生右键菜单能超出，是因为它是独立的系统对象）。

**已知限制（写进 README 了）**：被拖的图标超出面板后会被**窗口裁掉**
（窗口只有 72 逻辑像素高）。macOS 能让图标浮在 Dock 外，我们做不到 ——
除非拖拽期间加高窗口，而那会让透明区域吞掉桌面点击。被裁掉这件事本身
也顺带成了「要删了」的视觉反馈。

### 触发条件 —— 已触发并完成

### 验收标准

全部通过，见上表。补充说明：

- 「拖拽时鼠标移出 Dock 窗口再回来仍跟手」——`drive_drag_probe` 已证明事件不丢，
  且自检里那两次拖拽的终点都在窗口内/外各一次，都正确完成。
- **自动化只验证「结果正确」，没验证「好不好看」。** 让位动画顺不顺眼、
  红边与提示文字够不够醒目，仍然要人工看一眼。
- 自检过程中有两个坑记在代码注释里，都是**测试自身**的问题而非产品问题：
  ① `SendInput` 的 `cbSize` 传成数组长度 → 全程「注入 0 段」，看起来像环境不支持；
  ② 删掉的那项要先 **补回** 再 `reorder`，顺序反了会还原不到位；
  ③ 拖拽行程要按**起点**算：图标中心 clientY≈42，只往上拖 60 逻辑像素到不了
  `DELETE_MARGIN=26` 之外，断言会拿到 `<none>`。

## BL-5 右键菜单独立窗口 + 分割线

**状态：已完成（2026-09）。**

### 动机

两件事一起做，因为它们共用同一个入口（右键菜单）：

1. **菜单外观**。原实现用原生 `TrackPopupMenu`，两个不可接受的代价：
   外观完全无法定制（Windows 原生样式 vs Dock 的玻璃观感是两种东西）；
   而且它**自带模态消息循环**，会把调用它的线程整个卡住 ——
   旧代码必须专门丢到 `spawn_blocking` 里跑，否则 Tauri 的事件循环被卡死。
2. **分割线**。用户要「把图标分组」，而分组线必须能被用户自由摆放。

### 现状证据（实施前的代码位置）

| 位置 | 原状 |
|---|---|
| `menu.rs` | `show_and_run()` + `TrackPopupMenu` + `ID_ACTIVATE…ID_REMOVE` |
| `commands.rs::show_context_menu` | `spawn_blocking` 包住整个模态菜单 |
| `Dock.tsx` | 右键只把 `target_hwnd/target/app_id/...` 发给 Rust，Rust 侧直接执行动作 |
| `pinned` | 只有应用条目，没有「分隔」概念 |

### 实施方案（实际落地的）

**1. 分割线 = 列表里的普通条目**（不是单独一份位置数据）

- `model.rs`：`AppEntry.separator` / `PinnedApp.separator`，都带 `#[serde(default)]`
  （老配置读进来就是 `false`）。
- `apps.rs::enumerate_dock_apps`：遇到 `separator` 直接原样输出，**不参与「在不在运行」的匹配**。
- `store::add_separator(after)`：插在指定条目**后面**（找不到锚点就追加到末尾 ——
  用户的动作是「加一条」，唯一不能接受的结果是"点了没反应"）；
  id 用 `sep-<毫秒>-<序号>`，与应用 id（exe 全路径小写 / `uwp:<AUMID>`）天然不冲突。
- `Dock.tsx`：分割线复用**同一个 `<button>`**，这样它自动获得和图标完全一样的
  拖拽排序 / 拖出删除 / 右键能力；只换内容（一条竖线）。`SEP_W = 9`（线 1px + 可点中的空白）。
- **两侧间距比图标更紧**：`SEP_GAP = 4`（图标之间是 10）。
  第一版直接套用图标间距，于是 1px 的线两侧各留 `10 + 13/2 = 16.5px`，
  用户反馈「两侧空出来的距离太大」。现在每侧 8.5px。
  实现上 `computeLayout` / `maxMagnifiedWidth` 的间距参数从标量扩成**逐对数组** `gaps`。
- **不放大**：`computeLayout` 加了 `fixed?: boolean[]` 参数，分割线的倍率恒为 1，
  但仍参与排布（邻居照常让位）。行宽按 `SEP_W` 计，实测中途插一条 = **+7**
  （`9 + 4 + 4 − 10`，因为原来那两个图标之间本来有一个 10 的间距）。
- **颜色：三次才定下来**（这一条最值得看，因为它不是"喜好"问题而是"量出来"的问题）：

  | 版本 | 做法 | 实测结果 |
  |---|---|---|
  | 1 | 白线 0.55 + `box-shadow: 0 0 0 1px rgba(0,0,0,.22)` 描边 | 用户：**「中间白，四周黑，太明显」** —— 1px 的线被描成 3px 的黑白夹心 |
  | 2 | 单色中性灰 `rgba(120,120,128,.5)` | **完全看不见**：元素在、宽度对、DOM 断言全过，但肉眼没有 |
  | 3 | 单色浅色 `rgba(255,255,255,.42)`，无描边 | ✅ 1 物理像素宽、亮度 **178** vs 底色 **121**（差 57） |

  第 2 版为什么会栽：当时想的是一句听起来很对的话 ——「中性灰在明暗两边都有对比度」。
  但**玻璃是半透明的，渲染出来的底色由桌面内容决定**：本机量到的实际底色是
  `#797980`（约 121），跟那个"中性灰"几乎一模一样。
  所以颜色不能按**配置里的着色**选，只能按**渲染后的底色**选，而后者是动态的。
  结论：跟运行白点用同一套办法（浅色半透明）。桌面很亮时它同样会变淡 ——
  这是这套玻璃底座的固有取舍，白点也一样。

**2. 菜单改成第三个 WebView 窗口**（`panel.html` + `src/panel/`；后来文件夹面板也住进来，所以叫"浮层"）

- `menu.rs`：只管「该有哪些项」和「点了干什么」（纯逻辑，10 项单测）；
- `panel_window.rs`：窗口创建 / 定位 / 显示时序 / 隐藏的四条路径 / 看门线程；
- `panel_window.rs` 的模块注释里写了完整时序图与四条隐藏路径 —— **改动前先读那段**。

### 实测数据

| 指标 | 实测 |
|---|---|
| 菜单窗口矩形（iconSize 38 的配置） | 逻辑 168×210 → 物理 210×263 |
| 菜单水平锚定误差 | **0 物理像素**（菜单中心 == 右键光标） |
| 菜单是否抢焦点 | **没有**（前台始终是原来那个窗口） |
| 内容溢出 | `scrollHeight 211 ≤ clientHeight 211`（Rust 算的尺寸与 CSS 渲染一致） |
| 行宽增量 | 182 → 189（**+7** = 分割线 9 + 紧间距 4+4 − 原图标间距 10） |
| 分割线两侧可见空白 | 每侧 **8.5 逻辑像素**（图标之间是 10；第一版是 16.5，用户嫌太空） |
| 分割线渲染 | 1 物理像素宽 × 32 物理像素高；亮度 **178** vs 底色 **121**（差 57） |
| 自检 | `drive_menu_test` **22/22 通过**（`DOCK_MENUTEST=1`） |

### 两个踩到的坑（都已修，注释留在代码里）

1. **`GetAsyncKeyState` 只看 0x8000（当前按着）会漏掉点击**。
   合成点击（以及手很快的真实点击）的按下-抬起可能短于一帧（16ms），
   看门线程两次轮询之间就过去了 → 菜单开着点别处关不掉。
   必须同时看 **0x0001 位**（自上次查询后按过）。
2. **`hide()` 会连「当前浮层的目标」一起清掉**，所以 `panel_invoke` 必须
   **先取目标、再关菜单、最后执行**。反过来写会「菜单正常关闭、动作静默不执行」，
   表现就是「点了没反应」—— 这个 bug 是自检抓出来的，不是看代码看出来的。
3. **会改动 Dock 列表的自检必须先确认配置被重定向**（`require_temp_config`）。
   本轮真实配置被写脏过一次：菜单自检在配置里加了一条分割线，而那次运行
   中途被打断（超时被杀），还原步骤没跑到 —— 用户的 Dock 上就留下一条测试分割线，
   而且**事后从日志里看不出是哪一次留下的**。现在没有 `DOCK_CONFIG_DIR` 就直接拒绝跑。

### 验收标准（已满足）

- 分割线能加、能落盘、能拖动排序、能拖出去删除、能被右键移除；
- 分割线两侧的空白比图标之间更紧（每侧 8.5 逻辑像素），线本身只有 1 物理像素、无描边；
- 菜单：右键出现、贴 Dock 上方、以光标为中心、不抢焦点、Esc / 点别处 / 选一项都关闭、
  同一个图标再右键一次是开关；
- 视觉：`DOCK_MENUSHOT=<秒>` + 截屏核对（浅色 Dock → 浅色菜单 + 深色文字，
  蓝色悬停高亮，分隔线位置与深浅合适）。

### 怎么量「一条线看不看得见」（可复用）

DOM 断言查不出这个 —— 元素在、尺寸对、颜色也对，就是融进底色了。要量像素：

1. `DOCK_MENUSHOT` 或直接把 Dock 跑起来，用 `GetWindowRect` 拿 Dock 的物理矩形；
2. `SetProcessDPIAware()` 后 `CopyFromScreen` 把 Dock 抓成 PNG；
3. 在 **Dock 竖直中线**那一行逐个像素算亮度 `0.299R+0.587G+0.114B`；
4. 找局部极值 —— 那就是分割线，与两侧底色的差值就是"看不看得见"的量化指标。
   本机实测：底色 121、线 178（差 57）= 看得见但不抢眼；
   第 2 版中性灰那次这条扫描线上**什么都没有**，一眼就查出来了。

## BL-6 菜单窗口没有投影

**状态：待办（低优先级，只影响观感）。**

### 动机

macOS 的菜单有明显外投影，视觉上「浮」在桌面上。现在的菜单窗口没有投影，
只靠 1px 内描边区分边界 —— 在浅色桌面内容上会显得"贴"在上面。

### 现状证据

- 亚克力由 `SetWindowCompositionAttribute` 铺满**整个窗口矩形**（`glass.rs` 的模块说明）；
- 因此窗口不能比菜单内容大 —— 多出来的边距会变成一圈**染色**的边框，
  而不是透明到能画阴影的区域；
- 反过来，`box-shadow` 画在窗口内部会被窗口边界裁掉（`overflow: hidden` + 窗口就那么大）。

### 触发条件

用户提出「菜单看起来不够立体」时再动手。**不要**为了这一点去改窗口层结构 ——
收益（一点阴影）远小于风险（亚克力/圆角/DWM 那一套是踩了很多坑才稳住的）。

### 可能的方案（未验证，动手前先做 A/B 实验）

1. **窗口比内容大 N 像素，但不铺亚克力**：改用 CSS 半透明底 + `backdrop-filter: blur()`。
   ⚠️ 未验证：`backdrop-filter` 在**透明 Tauri 窗口**上是否真的能模糊到**窗口背后**的桌面
   （Chromium 的 backdrop 一般只作用于页面内部内容）。若可行，就能顺便拿到真投影。
2. **只用内阴影做"假立体"**：`inset 0 1px 0 rgba(255,255,255,.10)` 已有一点点，
   可以再加一条底部内暗边模拟厚度。

### 验收标准

菜单在**浅色**桌面内容上也能一眼看出是浮层（截图对比），且亚克力模糊观感不变差。

## BL-7 菜单窗口要不要按需创建

**状态：待办。有实测数字，但**先别急着改** —— 这是一个明确的取舍，不是 bug。**

### 动机

右键菜单是**第三个 WebView 窗口**，目前在启动时就创建好并隐藏（为了右键即时响应）。
代价是常驻内存。

### 现状证据（2026-09 实测，产品构建，Dock 4 个图标、菜单未打开）

| | 主进程私有 | WebView2 子进程 | 合计私有 |
|---|---|---|---|
| 菜单窗口是独立窗口之前（README 旧数字） | 8 MB | 6 个 / 183 MB | **191 MB** |
| 现在 | 7.7 MB | **7 个 / 234 MB** | **242 MB** |

也就是说：多一个 WebView 窗口 ≈ **+51 MB 私有内存**（主进程本身没变）。
进程数与私有内存是用 `Win32_Process` 的父子链筛出 `dock-app.exe` 的后代后逐个加出来的
（`Get-Process -Id … | PrivateMemorySize64`）。

### 为什么现在是"启动就建"

`WebviewWindowBuilder::build()` 会初始化 WebView2（几百毫秒）。第一次右键再建的话，
**那一次右键会明显卡一下** —— 而右键是高频动作，这个代价比内存更伤体验。

### 触发条件

只有在**用户抱怨内存占用**、或将来要支持低配机时才动手。
不要因为"242 MB 看起来大"就改 —— 它换来的是一次右键的即时响应。

### 实施方案（若决定改）

- `panel_window::create` 改成惰性：`show_menu()` / `show_folder()` 里发现没有窗口就先建（**并在建的过程中
  让 Dock 保持暂停隐藏**，建完再按正常流程显示）；
- 或者折中：**启动 20 秒后再建**（用户第一次右键之前基本已经建好了），
  这样启动瞬间的内存曲线更平；
- 无论哪种，`panel_window::show_menu` / `show_folder` 的调用方都不能假设窗口已存在
  （现在它们已经会返回「浮层窗口不存在」的错误，见 `panel_window.rs`）。

### 验收标准

改完之后：右键菜单首次出现的主观延迟 ≤ 一次 60Hz 刷新的观感（用
`DOCK_MENUSHOT` + 计时验证）、常驻私有内存下降接近 51 MB，
且 `DOCK_MENUTEST=1` 仍然 21/21。

## BL-9 系统位置（此电脑 / 回收站）

**状态：已完成（2026-09）。**

### 动机

用户要把「此电脑」「回收站」放进 Dock 最左侧。它们不是 exe，
而是 **Shell 命名空间项**，所以要先确认三件事都成立才动手。

### 现状证据（动手前实测的三条路）

| 需要 | 走哪条路 | 实测 |
|---|---|---|
| 显示名 | `IShellItem::GetDisplayName(SIGDN_NORMALDISPLAY)` | 中文系统 →「此电脑」「回收站」 |
| 图标 | `IShellItemImageFactory::GetImage`（认 shell 路径） | 128×128，透明像素 **41~42%**（真图标，不是一块底板） |
| 打开 | `ShellExecuteEx(lpFile="shell:MyComputerFolder", lpVerb="open")` | 真的开出**「此电脑 - 文件资源管理器」**窗口 |

第三条最关键，也最不该靠猜：`ShellExecuteEx` 的 `lpFile` 本来就吃 `shell:` 路径，
所以 `apps::launch` **一行分支都不用加** —— 「打开此电脑」和「启动 Edge」
是同一条代码路径。实测结果记在 `drive_location_test` 的输出里。

### 实施方案（实际落地的）

- 表驱动：`apps::SYSTEM_LOCATIONS = [(target, 兜底文案)]`，加位置只要加一行；
  托盘子菜单和插入逻辑都从这张表读；
- `apps::shell_display_name()` 问 Shell 要名字（**不写死文案**，虽然本项目没有 i18n，
  但系统名字本来就该由系统给）；
- `store::add_system_location()` 插到**最左侧**；已经在列表里就移到最左
  （菜单项承诺的就是"放到最左侧"，点两次结果一致，用户随时能拖回去）；
- 入口：**托盘 →「添加系统位置」**（子菜单）；
- `apps::is_shell_location()` 把系统位置与打包应用（`shell:AppsFolder\…`）分开：
  位置说「打开」、runas 置灰；打包应用说「启动」、runas 保留。

### 踩到的坑

- **`shell:AppsFolder\...` 也以 `shell:` 开头**。第一版我用
  `target.starts_with("shell:")` 当判据，会把所有打包应用（计算器、设置…）
  都说成「打开」并把 runas 置灰。判据必须是
  `is_shell_target && !starts_with(APPS_FOLDER_PREFIX)`，两个单测各钉一边。
- 托盘菜单的 `MenuItem` 是**泛型**（`MenuItem<R>`），`Submenu::with_items` 是
  4 个参数（没有 id），要 id 得用 `with_id_and_items` —— 和 `Menu::with_items`
  的签名不一样，别按直觉写。

### 验收标准（已满足）

- `cargo test`：名字非空、图标 ≥32px 且透明 >20%、判据不被打包应用带偏；
- `DOCK_LOCTEST=1`：真的打开两个位置并断言出现新窗口，然后**只关掉刚开的那个**
  （原有资源管理器窗口数不变）；
- 截图核对：此电脑 / 回收站的图标在 Dock 上正常渲染（不是首字母占位）。

## BL-8 回收站图标跟随空 / 满状态

**状态：已完成（2026-09）。**

### 落地（2026-09）

关键是**图标缓存键**：图标在页面里按 `path@size` 缓存，所以不清掉就永远停在第一次那张。
做法是把"里面有几项"当**版本号**编进键里：

- Rust 新增 `apps::recycle_bin_items()`（`SHQueryRecycleBinW(None, …)`，所有盘合计）
  + 命令 `get_recycle_bin_items`；
- 前端 `getIconImage(path, size, version)`，键变成 `path@size@version`；
  `App.tsx` 只在**Dock 上真的有回收站**时才去问项数（一次 shell 查询），
  其它 target 永远传 0（行为与以前完全一样）。

### 验证（2026-09）

给 `get_icon_bgra` 加了一条 `DOCK_DEBUG=1` 的诊断行（`[图标] 取 …`），
因为"页面到底有没有重新来取图标"从外面**看不见**（图标是缓存的）。然后：

```
① 启动后（回收站 1 项）        取 shell:RecycleBinFolder 次数 = 1
② 丢一个文件进回收站（→2 项）  次数 = 2   ← 版本号变了 → 缓存作废 → 真的重取了
③ 还原（→1 项）               次数 = 2   ← 回到**见过的**版本号，命中旧缓存，不再重取（正确）
```

第 ③ 条不是 bug：1 项的图标和当初那张一模一样，复用缓存正是想要的（省一次抽取）。

**没验到的部分**：`0 项`（空）与 `>0 项`（满）的**图案差异**没法在这台机器上直接看 ——
用户回收站里有东西，清空它 = 删用户的文件，不能干。依据是 Shell 的定义：
`CLSID\{645FF040-…}\DefaultIcon` 下 `(Default)`（满）与 `empty`（空）是两个不同的图标资源，
资源管理器就是靠这个换图标的 —— 想亲眼看的话，清空回收站即可。

### 动机

Windows 的回收站有**两个图标**（空 / 满）。Dock 上的图标取自
`IShellItemImageFactory`，本身是正确的，但前端有缓存 ——
**Dock 启动时取的那一张会一直用到下次启动**。所以把文件删进回收站之后，
图标还是空的。

### 现状证据

- 图标缓存：`app/src/lib/ipc.ts` 的 `iconCache`，键是 `${target}@${size}`；
- 取图标：`app/src-tauri/src/icons.rs::extract_icon`（走 `IShellItemImageFactory`）；
- 系统位置表：`app/src-tauri/src/apps.rs::SYSTEM_LOCATIONS`（含 `shell:RecycleBinFolder`）。

### 实施方案（没做，仅供参考）

1. Rust 侧加一个轻查询：`SHQueryRecycleBinW(null, &mut info)` →
   `info.i64NumItems` / `i64Size`，只有"有没有东西"这一个 bit 有用；
2. 把它塞进 `list_apps` 的返回值（或做成一个独立的小命令），前端在
   指纹里带上它；**变化时**给 `getIconUrl` 传一个 cache-busting 后缀
   （例如 `shell:RecycleBinFolder#1`）逼它重取一次。

⚠️ 不要每轮都重取 —— 图标提取是 `IShellItemImageFactory::GetImage`，
比枚举窗口贵得多（`enumerate_apps` 整轮才 2.6ms）。只在"空满状态翻转"时取一次。

### 触发条件

用户抱怨「我删了文件，回收站图标没变」时。它是纯观感问题，不影响任何功能。

### 验收标准

把文件删进回收站（或清空）之后 2 秒内，Dock 上的回收站图标跟着变，
且空闲 CPU 不变（`docs/backlog.md` 附录 A 的测法）。

## BL-10 图标光学尺寸与视觉间距

**状态：已完成（2026-09）。**

### 动机

用户反馈「左侧那三个图标的间隔太大」。**先说结论：布局没有任何问题** ——
量出来相邻间距全是 `10.0`，很均匀。问题在**图形自己在画布里留的白不一样**：

| 图标 | 图形占画布宽 | 每侧留白（iconSize=38） |
|---|---|---|
| 回收站（Windows shell 图标） | 75% | 4.8 逻辑像素 |
| 此电脑（Windows shell 图标） | 88% | 2.4 |
| Edge / Chrome / QQ / 微信 | 100% | 0 |

视觉间距 = 布局间距 + 左图右留白 + 右图左留白，于是实测：
**此电脑↔回收站 17.1、回收站↔资源管理器 14.8、应用之间 10.0**。用户看到的是真的。

### 现状证据（怎么量的）

自检 `DOCK_ICONBOX=1` 一次打印三层，**三层都要看才定位得到改哪一层**：

1. **布局间距** —— 页面里 `getBoundingClientRect()` 逐个算（逻辑像素）；
2. **图标原始留白** —— Rust 侧 `icons::alpha_bbox(threshold=8)`，指的是 shell 给的原始图标；
3. **渲染后的留白与视觉间距** —— 把 `<img>` 的 data URL 解回来，在页面里用
   `OffscreenCanvas` 扫 alpha 包围盒。这一层才是眼睛看到的（中间隔着前端的归一化）。

### 实施方案（实际落地的）

1. `lib/ipc.ts::encodeOptical`：把图形放大到在画布内尽可能大，
   `k = min(画布宽/图形宽, 画布高/图形高, 1.6)`，以**包围盒中心**为基准（不重新居中，
   图标是底边对齐的）；并把归一化后的横向留白 `insetX` 一起回报。
2. `Dock.tsx::gapBetween`：相邻间距 = `max(MIN_GAP, gap − 两人留白)`，
   于是**视觉间距**对所有图标一致。初始布局与拖拽让位预览共用这一个函数。
3. `getIconImage()` 取代原来的 `getIconUrl()`（后者保留为薄封装，设置页还在用）。

### 踩到的坑

- ❗**不能让图形超出画布**。第一版给了 1.1 倍纵向余量（想让高瘦的回收站横向填满），
  结果 `drawImage` 把图形**裁掉**了一条 —— 画布就是边界，"纵向溢出"只是被切掉而已。
  自检里那句「贴边」就是查这个的（配合第 2 层的原始包围盒反推倍率才能确认是"正好填满"
  还是"被裁"）。
- ❗**断言别写死间距**。菜单自检里「加分割线后行宽 +7」是按"图标间距恒为 10"算的，
  改成光学间距之后被顶掉的那个间距变成了 6.4（因为旁边是回收站），断言就挂了。
  正确写法是**先量出将被顶掉的那个间距**再算期望值。
- 三层测量的顺序也有讲究：只看第 3 层会以为"图形本来就小"，只看第 1 层会以为"布局没问题"，
  两者都是对的但都不能定位原因。

### 验收标准（已满足）

- 视觉间距：`此电脑↔回收站 10.0`、`回收站↔资源管理器 10.0`、应用之间 `10.0`（修前 17.1/14.8/10.0）；
- 对应布局间距变成 `6.4 / 6.5 / 10.0`（该紧的紧，应用之间不动）；
- 应用图标**一点没变**（倍率算出来是 1，不重新编码）；
- 全量自检回归：拖拽 7/7、菜单+分割线 22/22、系统位置 4/4。

## BL-11 大文件夹（程序坞文件夹）

**状态：已完成（2026-09）。**

### 动机

用户要"像手机桌面大文件夹那样"的东西：**占一个图标位**，点开在原地展开里面的一堆应用，
**不是弹窗、不是跳转页面**。

### 现状证据（动手前的约束）

- Dock 窗口只有 `panelHeight`（默认 72）逻辑像素高 —— **页面里画不下任何浮层**，
  "窗口是透明的" ≠ "内容能画到窗口外"（这条在 BL-5 已经吃过一次）；
- 所以展开必须落到**另一个窗口**上。但"另一个窗口"要看起来不像弹窗，就得：
  同一材质（亚克力）、贴 Dock 上方、以点击的图标为中心、无边框无标题、
  点别处/Esc 关闭、**不抢焦点**；
- 这些恰好就是 BL-5 给右键菜单做好的那一整套（含看门线程）。

### 实施方案（实际落地的）

1. **和右键菜单共用浮层窗口**（`panel_window.rs`，页面按 `content.kind` 分支渲染）。
   于是**同一时刻只可能有一个浮层** —— 打开文件夹自动关掉菜单，反之亦然，
   而那本来就是想要的行为。省掉了把看门线程/显示时序抄第二遍。
2. **数据模型**：文件夹是 `pinned` 里的普通条目（`is_folder` + `children`），
   孩子不占顶层位置。于是它自动能拖、能删、能被右键。
   `store::remove` 改成**顶层和文件夹里都找** —— 用户眼里的"移除"不分层级。
3. **三条交互**（全部实测）：
   - 右键图标 →「新建文件夹」：**原位**变成文件夹，自己成为里面第一个；
   - 把图标**拖到**文件夹上：放进去（拖拽期间文件夹描蓝边）；
   - 右键文件夹 →「解散文件夹」：孩子回到顶层、放在文件夹原来的位置。
4. **Dock 图标**：前 4 个孩子的缩略图 2×2 预览（取 4 个就够，多取是白花时间）。
5. **面板尺寸**：列数 / 格子边长 / 间距 / 内边距全在 Rust 算，通过 payload 给页面；
   行数受**屏幕可用高度**约束（最多 5 行），超出滚动 —— 面板必须整个在 Dock 上方。

### 踩到的坑

- ❗**两层浮层不能各起一个看门线程**：`GetAsyncKeyState` 的 0x0001 位
  （"上次查询之后按过"）是**一次性的**，谁先查谁拿到。两个线程各查一次，
  合成点击（按下+抬起短于一帧）只会被其中一个看到 —— 如果是"没轮到关"的那层
  拿走了，这次点击就凭空消失。症状很怪：**点外面关不掉菜单，再点一次却把菜单关了**。
  现在整个栈只有一个看门线程，每 tick 取一次 `top_slot()` 再决定关谁。
  退役时"先清标志再复查一次"，堵住 `ensure_watchdog` 与它擦肩而过的窗口。
- ❗**启动竞态：初值定位覆盖掉前端上报的尺寸**。窗口层初始化是**异步投递到主线程**的
  （`supervise`），而这轮改成启动时创建**三个** WebView（Dock + 文件夹 + 菜单），
  同步建窗把主线程占住了几秒 —— 于是那句"先用初值 520 定位"排到了页面首次上报**之后**，
  把真实宽度覆盖掉，而且之后不会再有人上报（宽度没变）→
  **Dock 永久停在初值宽度**（面板比内容宽一大截、两边全空）。
  实测曲线：`650 → 325（空状态的报告）→ 650（被初值覆盖）→ 一直 650`。
  两层修：① 浮层窗口改到窗口层就绪**之后**再建（`supervise` 里延时 1.5s 投递）；
  ② `set_dock_size` 记一个"已上报"标志，窗口层初始化看到就不再动它。
- ❗**两个浮层窗口共用一个页面时，读 DOM 必须读对窗口**。
  自检原来用 `get_webview_window("panel")` 当"菜单窗口"（那时只有一个浮层），
  拆成两层之后它读的是文件夹窗口，于是菜单相关断言全挂成了
  `菜单中心 221 vs 光标 766`、`页面 null/6 项` 这种**看起来像产品问题**的数字。
  现在测试里 `menu_win` / `folder_win` 分开取，各自的 DOM 各自读。
- ❗**点文件夹里的图标"没反应"**：`panel_launch` 把**应用 id** 当成了**菜单项 id**
  传给动作层（`menu::run(a, &target, &item_id)`），于是落进
  `_ => Err("未知的菜单项")` —— 错误还被 toast 掉，界面上就是"点了不开"。
  两个 id 在同一个函数里长得一样（都是 `String`），编译器帮不上忙；
  现在传的是 `menu::id::ACTIVATE` 常量，并且自检里真的**点一下**、断言
  资源管理器窗口数增加（`0 → 1`）。
- ❗**面板里右键弹出的是浏览器的菜单**：面板页面没处理 `contextmenu`，
  WebView2 就弹它自己的「刷新 / 检查」。Dock 页面早就拦了，面板漏了。
- ❗**「移出文件夹」把图标删了**：文案和行为不一致 —— 用户读"移出"是"挪出去"，
  而实现复用了 `store::remove`（彻底删）。现在分成两个菜单项：
  文件夹里是 `MOVE_OUT`（挪到顶层、放在文件夹**后面**），顶层才是 `REMOVE`（删掉）。
  顺带给文件夹的「移出 Dock」加上项数 —— 它会把里面的一起删掉，
  不写清楚就是静默的数据损失。
- ❗**白点变黑点**：面板的 `.folder-dot` 按主题分了深浅两套，浅色主题下画成黑的。
  但白点是"这个应用开着"的**统一视觉语言**，同一块材质上换个颜色会被读成另一种状态。
  现在**永远是白的**（和 Dock 的 `.dock-dot` 一致），只加一层很淡的暗描边。
- ❗**tag 枚举上的 `rename_all` 不改变体里的字段名**（这一条最值得记）。
  `PanelContent` 是 `#[serde(tag = "kind", rename_all = "camelCase")]` 的枚举，
  而枚举级的 `rename_all` **只改变体名**（`Menu` → `menu`）。
  漏掉变体级的 `#[serde(rename_all = "camelCase")]` 之后，Rust 发的是
  `row_h` / `divider_h`，页面读 `rowH` / `dividerH` 全是 `undefined` ——
  **菜单行高整体失效、挤成一条**。为什么难发现：`items` 恰好两边同名、
  payload 级的字段在枚举外面所以正常 —— 数据"看起来是通的"，
  **tsc 查不出来、既有断言也全过**。现在用
  `payload_field_names_are_camel_case` 把"页面读哪些字段名"钉死了。
- **空文件夹点开会"没反应"**：`show_folder` 返回「这个文件夹是空的」，
  而前端原来只 `console.warn`。改成弹 toast。
- **运行点的归属**：文件夹自己**不该有白点**，里面**在跑的格子**才点。
- **改名不只是改文件名**：`menu.html` → `panel.html` 还牵动 `vite.config.ts`、
  页面里的 `<script src>`、以及按 DOM 选择器做的断言。
- **别被构建类型骗到**：`cargo build` 会把 `--features selftest` 的产物**原地覆盖**。
  现在启动横幅里会打印 `构建 自检脚手架 开启/关闭`。

### 一条经验（这轮 8 个 bug 里有 4 个是同一类）

**"接了线但没点过"的路径一定有 bug。** 出问题的几条全是"Rust 函数写好了、
前端也接上了，但从来没有人真的点一下"：点文件夹里的图标、面板里右键、
移出文件夹、逐层关闭。它们的共同点是**没有走过完整链路就被算作完成**。
所以自检里凡是新增一条交互，都要**真的合成一次输入**并断言可见结果
（窗口数变化 / 配置结构变化 / DOM 变化 / 哪一层还开着），而不是只断言"函数返回 Ok"。

### 验收标准（已满足）

`DOCK_MENUTEST=1` 的「大文件夹」段 17 项全过（**真实交互**）：

```
[PASS] 右键「新建文件夹」：原图标**原位**变成文件夹，自己成了里面第一个
[PASS] 点文件夹图标 → 展开浮层，网格里就是里面那一项
[PASS] 文件夹图标上**没有**白点（白点是应用的，不是文件夹的）
[PASS] 面板里右键图标 → 弹的是**它自己的菜单**（含「移出文件夹」）
[PASS] 在文件夹里右键 → 菜单和文件夹**同时开着**（文件夹没被关掉）
[PASS] 点菜单外面 → **只关菜单**，文件夹还开着
[PASS] 再点一次外面 → 文件夹才关掉（逐层关闭）
[PASS] Esc 也是逐层：先关菜单、再关文件夹
[PASS] 点文件夹里的图标 → 真的打开了（不是点了没反应）  「回收站」窗口 0 → 1
[PASS] 「移出文件夹」把它挪到**顶层**（文件夹后面），不是删掉
[PASS] 文件夹面板贴在 Dock **上方**（像是从图标里长出来的）
[PASS] 把图标拖到文件夹上 → 进了文件夹（顶层少一个，文件夹里多一个）
[PASS] 展开后：**在跑的那一格**有点、没在跑的不点（本次含在跑的应用）
[PASS] 右键文件夹 → 菜单给「解散文件夹」和「移出 Dock」
[PASS] 文件夹的「移出 Dock」写明了会连里面几项一起删
[PASS] 「解散文件夹」：里面的条目回到顶层，文件夹本身消失
小结：40 项通过（菜单 21 + 大文件夹 19），0 项失败
```

## BL-12 层级：Dock 只在桌面层，浮层永远最上

**状态：已完成（2026-09）。**

### 动机

用户原话：「dock 栏的层级问题，dock 栏应该只在主桌面上，其他页面都应该在他之上」。

原设计（§3.2）把 Dock 主窗口写成 `TOPMOST`，`always_on_top: true`。后果是**打开任何应用之后
Dock 还压在那个应用上面** —— 一个全屏的浏览器下面永远横着一条 Dock，像贴纸一样洗不掉。
Windows 自己的任务栏是 `TOPMOST`（因为它要在任何情况下可用），但我们的需求正好相反：
**Dock 是桌面的一部分，不是系统外壳。**

### 现状证据（动手前的约束）

代码里把 Dock 顶到最前的地方**有三处，不是一处**：

| 位置 | 原样 | 后果 |
|---|---|---|
| `tauri.conf.json` / `main.rs` | `alwaysOnTop: true` | 建窗就是置顶，且 `SetWindowPos` 之外无人能改回去 |
| `win_layer::layout_dock` | `SetWindowPos(..., HWND_TOPMOST, ...)` | 每次自动隐藏 / 重排都把 Dock 顺手顶到最前 |
| `reveal::move_to` | `HWND_TOPMOST` | 进出屏动画改 Z 序 —— Dock 每次显示后都跑到所有窗口上面 |

只改第一处会得到一个"偶尔置顶"的 Dock（显示一次就顶上去），比不改更难查。

### 实施方案（实际落地的）

1. `always_on_top(false)`；
2. `layout_dock` 的 `SetWindowPos` 换成 `SWP_NOACTIVATE | SWP_NOZORDER`；
3. `reveal::move_to` 同样 `SWP_NOACTIVATE | SWP_NOZORDER`。

浮层窗口（`panel` / `menu`）**保持不变，仍然是 `TOPMOST`** —— 菜单和大文件夹是"用户刚刚要求
出现的临时界面"，被新打开的应用盖住就等于"点了没反应"。所以现在是**两档 Z 序**，不是一档。

### 风险与未验证点

- **最大化的窗口会盖住 Dock**：这是"只在桌面上"的直接推论，刻意接受。要改的话正确做法是
  **只对最大化窗口特判**（`IsZoomed`），不是整体恢复置顶。
- 浮层是 `TOPMOST`，所以独占全屏游戏里同样看不到（老限制，见 README「已知限制」）。
- 未验证：多显示器下把 Dock 放在副屏时，主屏的最大化窗口行为（应在同一屏内讨论，未测）。

### 触发条件

用户抱怨"开着应用时 Dock 还压在上面"时。修之前先确认是**哪一处**在置顶（三处都要看）。

### 验收标准（已满足）

```
1) 无遮挡时 Dock 中心点最上层：      'Dock'
2) 普通窗口盖住该点后：              'ZTEST-COVER'   ← 需求达成
3) 同一个窗口改成 TopMost 后：        'ZTEST-COVER'
4) 关掉遮盖窗口后：                  'Dock'
样式：Dock EX=0x8000190 TOPMOST=False；'Dock 浮层' / 'Dock 文件夹' EX=0x8000198 TOPMOST=True
```

（第 4 相是关键：证明 Dock 不是"被关掉的窗口挡住看不见"，而是真的回到了最上层。）

## BL-13 悬停名字：自己画，不用原生 tooltip

**状态：已完成（2026-09）。**

### 动机

用户原话：「我看你调用的时原生窗口，很丑，改一下，改成和 mac 一样的逻辑，在图标上方显示」。

早期实现是给图标按钮加 HTML `title` 属性 —— 最省事，但 `title` 由 **WebView2 宿主**画成
一个原生 tooltip 窗口：系统字体、系统圆角、固定在光标**右下角**、约 1 秒后才出现。这三点
（外观、位置、时机）全都不可控，和 Dock 的 macOS 观感不是一套。而 Dock 是本项目里**唯一**
可以完全自绘的界面，把名字提示交给系统画等于白送一块。

### 现状证据（动手前的约束）

- `Dock.tsx` 里每个图标是 `<button title={item.name}>` —— 删掉 `title` 会**一起丢掉可访问性**；
- 浮层窗口已经有一套完整的"贴 Dock 上方居中 + 不抢焦点 + 看门关闭"的机制
  （`panel_window.rs` 的 `Slot`），重画一个气泡等于把那些坑再踩一遍；
- 锚点用 `e.clientX` 是错的：光标可以从图标**边缘**进入，那样标签会被推到图标外侧。

### 实施方案（实际落地的）

复用**菜单层的窗口**（不新增 WebView），加一种 `PanelContent::Label { text, font_size }`：

| | 做法 |
|---|---|
| 外观 | `panel.html` 里 `.panel-label`：和菜单同材质、同圆角、同字号 |
| 位置 | `place()` 复用同一套规则：底边贴 `dock.top - GAP_ABOVE_DOCK`，**水平以图标矩形中心**为中心并钳进工作区 |
| 时机 | `App.tsx` 120 ms 延迟 + `hoverRef` 去重（进出同一个图标不重复弹） |
| 锚点 | `onMouseEnter` 里 `e.currentTarget.getBoundingClientRect()` 的中心，**不是 `clientX`** |
| 可访问性 | `title` → `aria-label`（别把无障碍一起删了） |
| 冲突 | 菜单真开着时不弹标签 —— 同一个窗口，弹了会把菜单顶掉 |

### 风险与未验证点

- 标签和菜单**共用一个窗口**，所以"菜单开着时悬停图标"没有标签。可接受（用户正看着菜单，
  标签也没意义），但如果以后要两者同屏，就得再开一个 `Slot`。
- 标签宽度由 Rust 用 `text_width()` 估算（`LABEL_FONT=13`），**字体度量变化会偏**。
  实测「文件资源管理器」139×29 物理像素不裁字；更长的名字（如打包应用的完整描述名）未逐个验证。
- 未验证：高 DPI（>150%）下标签宽度与锚点是否仍精确（本轮只测了当前缩放）。

### 触发条件

用户抱怨名字提示的外观 / 位置 / 出现太慢时。

### 验收标准（已满足）

```
悬停文件夹图标 → 弹出 'Dock 浮层' 窗口 139×29 @ (554,911)
Dock 矩形 (453,950)-(1466,1020) → 标签底边 940 < Dock 顶 950（在图标正上方，不相交）
窗口样式：WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW（不抢焦点、不进 Alt+Tab）
文件夹里的格子：气泡贴的是**文件夹面板**的上方（`place` 的 `base` 换成面板窗口）
```

### 补：底色提亮（用户第二轮反馈"颜色有点暗"）

第一版让标签**沿用 Dock 的着色**（默认 `[24,24,28]`）+ 深色遮罩，渲染出来是
"中灰玻璃压着白字"：实测底色亮度 ~147，白字与它对比不到 2:1 —— 看着发闷。

改法：**只给标签**把着色往白里提 `LABEL_BRIGHTEN = 0.62`（`[24,24,28] → [167,167,170]`），
菜单与文件夹不动。提亮之后 `is_dark(tint)` 自然翻面 → 页面用深色文字，
对比度从 ~1.9 升到 8 以上（`is_dark` 的 0.18 门槛本身就是按 WCAG AA 推出来的）。

| | 底色亮度（左右内边距处取样） | 平均亮度（含文字） |
|---|---|---|
| 改前 | 146.4 – 153.1（随桌面内容浮动） | 131.1 |
| 改后 | **191.0**（9 个图标全部一致） | 163.0 |

复现方法：合成鼠标移到图标上 → 取 `Dock 浮层` 窗口矩形 → `CopyFromScreen` 后
只取**左右内边距**那几列（文字在中间，避不开就量不准）算 sRGB 加权亮度。
`cargo test` 里立了闸：`label_tint_is_bright_enough_to_flip_text_color`
（既要真变亮 >100 级，又要真的走出深色区，否则白字压中灰 = 改了更糟）。

### 踩到的坑（复用窗口的代价）

标签和菜单**共用同一个窗口**，于是也共用"当前条目 id"（`Open::target_id`）。
而"同一个图标再右键 = 关掉菜单"这条规则是按 id 判的 —— 结果：
**右键一个正显示名字的图标，被当成"再点一次"**，标签关掉、菜单不弹。
自检里的表现是 `[FAIL] 右键图标 → 独立菜单窗口已显示`，
而打印出来的"菜单矩形"是 `74x29`（标签的尺寸），一看就不是菜单。

修法：`Slot::same_menu_open()` —— 只有"已经显示着**同一条目的真菜单**"才算再点一次，
`PanelContent::Label` 不算。**教训：窗口可以复用，状态机不能复用得太随意 ——
凡是"按 id 判断当前是什么"的地方，都要连内容形态一起判断。**

## BL-14 自动隐藏任务栏的留空：别问"现在藏着吗"

**状态：已完成（2026-09）。**

### 动机

`reserveTaskbar`（默认开）的承诺是"Dock 与任务栏并存、互不遮挡"。用户机上任务栏是
**自动隐藏**的，实测却发现 Dock 的底边整段压在任务栏的弹出区上 —— 鼠标移到 Dock 图标上
就顺手把任务栏叫出来，而任务栏是 `TOPMOST`，于是它盖住 Dock。

### 现状证据（动手前的约束）

旧实现（`win_layer::taskbar_info`）：

```rust
let auto_hidden = r.top >= screen_h - 4;   // ← 看"此刻"的位置
if tb.auto_hidden { bottom -= tb.height; } // ← 只有"此刻藏着"才留空
```

问题在于**自动隐藏的任务栏一触底就弹出来**，那一瞬间它顶边回到 1020，"看着像常显"，
于是判断成不需要留空；可 `rcWork` 仍然是整屏（`SPI_GETWORKAREA` 实测 `(0,0)-(1920,1080)`、
`GetMonitorInfo.rcWork` 同样），所以 Dock 就贴到了 1080。

实测（1920×1080，任务栏 60px 自动隐藏）：

| | Dock 矩形 | Dock 图标行中心的最上层窗口 |
|---|---|---|
| 修前 | `(453,1010)-(1466,1080)` | `Shell_TrayWnd`（任务栏） |
| 修后 | `(453,950)-(1466,1020)` | `Dock`（任务栏弹出时也是 `Dock`） |

修前还**随启动时机随机**：任务栏恰好在启动那一刻是弹出的，Dock 就贴底；恰好是收起的，
Dock 就正确上移 60px。（本轮先量到的就是"正确"的那次，所以一度以为没问题。）

### 实施方案（实际落地的）

两个"与弹出/收起无关"的值：

1. 是不是自动隐藏 → `SHAppBarMessage(ABM_GETSTATE)` 的 `ABS_AUTOHIDE` 位
   （实测 `state=0x1`：自动隐藏开、非置顶）；
2. 要留多高 → `SHAppBarMessage(ABM_GETTASKBARPOS)` 的 `rc`（**吸附矩形**，
   实测 `(0,1020)-(1920,1080)` → 60px），并检查 `uEdge == ABE_BOTTOM`。

再加一道保险：只有 `wa.bottom >= GetSystemMetrics(SM_CYSCREEN)`
（工作区真的顶到屏幕底）才扣，免得某些外壳已经把任务栏排除了还扣第二遍。

### 风险与未验证点

- **任务栏不在底边**（左/右/顶部）时不做预留：`at_bottom == false` 就跳过。
  那种布局下 `rcWork` 一般会正确排除任务栏，但**没实测过**。
- 任务栏高度变化 / 换边后**不会自动重算**（R13 老问题），要重启或改设置才生效。
- 多显示器时 `SM_CYSCREEN` 是主屏高度，副屏上的任务栏高度未验证。

### 触发条件

用户报"Dock 被任务栏盖住"或"Dock 贴着屏幕最底边"时。

### 验收标准（已满足）

```
修后：Dock (453,950)-(1466,1020)  图标行中心 (960,985)
  该点最上层 = class='Tauri Window' title='Dock'
任务栏弹出后（光标在最底边 960,1079）：
  Dock 还是 (453,950)-(1466,1020)
  图标行中心最上层 = class='Tauri Window' title='Dock'
  任务栏区域 1020-1080 内一点 (960,1050) 最上层 = class='Shell_TrayWnd'
```

**副产品**：这个 bug 是"自检大面积报红"的真凶 —— Dock 被弹出的任务栏盖住以后，
所有**需要真实输入**的检查（拖拽排序、右键菜单、焦点矩阵 `[C]` 相）全部失败，
而只读 DOM 的检查照样通过。看到"只读的全过、要点的全挂"就该先怀疑遮挡，别怀疑被测逻辑。

## BL-15 Steam 游戏：白点与「切到前台」

**状态：待做（已支持添加与启动，缺的只是运行态）。**

### 动机

用户问"Steam 上下载的游戏怎么加进 Dock"。现在**已经能加、能启动、图标也对**
（`.url` 快捷方式，见设计文档 §4.2），但那条图标**永远没有白点**、
点它永远是"再启动一次"而不是"把游戏切到前台" —— 因为 Dock 判断"在不在运行"
靠的是**进程 exe 路径 = target**，而 `.url` 不是进程。

### 现状证据（动手前的约束）

- `.url` 里能拿到 `URL=steam://rungameid/<appid>`；
- `D:\Steam\steamapps\appmanifest_<appid>.acf` 里有 `"installdir"`（实测 `wallpaper_engine`）；
- 游戏真正的进程是 `steamapps\common\<installdir>\` 下面的某个 exe
  （Wallpaper Engine 是 `wallpaper32.exe` / `ui32.exe`，**不是** `.url` 里 `IconFile` 指的 `launcher.exe`）；
- 其他盘的游戏要读 `libraryfolders.vdf` 才能找到库根目录（用户机上 Steam 在 `D:\Steam`）。

### 实施方案（下次做的时候）

1. `apps.rs` 加 `steam_game_dir(url) -> Option<PathBuf>`：appid → 注册表 `HKCU\Software\Valve\Steam\SteamPath`
   →（`steamapps\appmanifest_<id>.acf` 或遍历 `libraryfolders.vdf` 里的库）→ installdir；
2. 运行态匹配从"exe 路径相等"放宽到"**exe 路径在这个目录下**"（只对 `.url` 条目生效）；
3. 匹配到就把那个窗口句柄带上，于是"切到前台 / 最小化 / 关闭窗口"三件套自动可用。

### 风险与未验证点

- **启发式**：目录里有别的进程（反作弊、启动器）也算"游戏在跑"；
- 一个目录里放了两个游戏（合集）时会互相误判；
- Epic / Battle.net 的 `.url` / `.lnk` 各有各的格式，这套只对 Steam 成立。

### 触发条件

用户说"游戏在跑但 Dock 上没有白点"或"点了只是又启动一次"时。

## BL-16 任务栏背景透明：查清了，**不做**（Win11 必须注入 explorer）

**状态：已撤销（2026-09）。曾经实现过一版，方向错了，代码已删。**

### 动机

用户两次提出：

1. 「在设置页面加一个调节任务栏背景透明度的选项」
2. 「不是把亚克力板放到任务栏的背景上，是我们直接修改任务栏的背景，使他可以达到透明的地步，
   让任务栏后面的壁纸显示出来」——并指名参考 **TranslucentTB**。

### 第一版错在哪（已删）

第一版用 `SetWindowCompositionAttribute` + `ACCENT_ENABLE_ACRYLICBLURBEHIND` 往
`Shell_TrayWnd` 上敷亚克力（和 Dock 自己同一条 API），做了开关 + 透明度滑块。
**实测它只能让任务栏更实**，方向与需求相反：

| 施加的东西 | 与系统默认的像素差 |
|---|---|
| 透明渐变（state 2）alpha=0 | 5.6 |
| 亚克力 alpha=1 | 6.3 |
| 亚克力 alpha=120（当时给的默认） | **17.5** |
| 模糊（state 3）alpha=0 | **30.0** |
| 透明渐变 alpha=255 | **35.3** |

（还原本身是干净的：`ACCENT_DISABLED` 后与基线逐像素一致，0%/1.5。）

### 为什么做不到"不注入"

- 任务栏背景是 **XAML 画的**。本机 build 26200 的子窗口结构里有
  `Windows.UI.Composition.DesktopWindowContentBridge`（XAML 岛）**铺满整条任务栏**
  `(0,1020)-(1920,1080)`；`SetWindowCompositionAttribute` 改的是窗口背板，
  背板之上那层不透明 XAML 内容它改不动。
- **DWM 背板路线也排除**：`DWMWA_SYSTEMBACKDROP_TYPE` 当前就是 0（`DWMSBT_AUTO`），
  设成 `DWMSBT_NONE` / Mica / Acrylic / Tabbed 之后**截屏逐像素无变化**。
- 老代码里的 `WorkerW` 路线（早期 22621 用它画任务栏背景）在本机**没有这个子窗口**。

### TranslucentTB 到底怎么做的（读它的源码）

```
SetWindowsHookEx(WH_CALLWNDPROC, proc, 自己的DLL, explorer 线程 id)   ← 注入
  → explorer 里 InitializeXamlDiagnosticsEx(...)                     ← Windows.UI.Xaml.dll 未公开导出
  → IXamlDiagnostics 遍历 XAML 可视树 → 改任务栏背景元素的 Background 画笔
```

`ExplorerTAP/` 共 10 个文件 ~25KB C++（COM proxy/stub、Detours payload、XamlBlurBrush），
依赖 vcpkg + C++/WinRT 工具链，代码里自带「Windows 更新后需重启 Explorer」的提示
（`IDS_RESTART_REQUIRED`）。**许可是 GPL** —— 抄进来本项目许可要跟着变。

### 结论与出口

- 本项目**不做**（与风险登记册 R10「不注入任何进程」一致，也与"不改注册表、不重启 Explorer"
  这条既有取舍一致）；
- 要完全透明的任务栏，用 **TranslucentTB** 或 **Windhawk** 的 taskbar 模块 ——
  它们就是专门干这个的，和 Dock 不冲突（一个改任务栏、一个是自己的窗口）；
- 第一版的代码（`taskbar.rs` / 开关 / 滑块 / `glass::disable_accent` / `RunEvent::Exit` 钩子）
  **已全部删除**；设置页「位置 → 任务栏」里留了一段注释说明为什么没有这个开关。
- 实测细节与结构 dump 见设计文档 §4.1.3。

### 未验证 / 遗留

- 注册表路线（`TaskbarAcrylicOpacity` / `UseOLEDTaskbarTransparency` + 重启 Explorer）
  **没有实测**：它是 Win10 时代的做法，在本机 26200 上大概率无效（背景是 XAML 画的），
  且要重启 shell 才能验证 —— 需要用户明确同意才做。
- 若哪天要改成"注入"，必须单独立一个 C++ 模块 + 新工具链，不要混进 Dock 主程序。

## BL-17 空文件夹：最后一个子项被「移出文件夹」之后留下的空壳

**状态：已完成（2026-09）。做法选了"自动解散"，并且顺手把逻辑抽成纯函数来测。**

### 落地（2026-09）

`store::move_out_of_folder` 里的逻辑抽成 **`move_out_of_folder_in(&mut Vec<PinnedApp>, child_id)`**
（不碰 `AppHandle`，于是能单测）。移出最后一项时它**原地解散**文件夹：把文件夹从列表里
拿掉、把该项插回**文件夹原来的下标** —— 用户看到的是"文件夹变成了那个图标"，
而不是"文件夹旁边多了一个图标、文件夹还在"。

单测 `store::tests::move_out_keeps_folder_until_last_child_then_dissolves_in_place`
一次覆盖四条：① 还有子项时文件夹留着、移出的项落在文件夹**后面**；
② 移出最后一项 → 文件夹消失且该项**原地接替**；③ 不在任何文件夹里 → 明确报错；
④ 顶层已有同 id → 拒绝（否则会出现两个同名图标，「移出 Dock」只删得掉一个）。

> **为什么值得抽纯函数**：这段逻辑原来和 `AppHandle` 缠在一起，只能靠自检慢慢跑（两三分钟、
> 还要合成鼠标）；抽出来之后 4 条断言 0.01 秒跑完，而且失败信息直指哪一条不成立。

### 动机

`store::move_out_of_folder` 只把子项挪到顶层，**不动文件夹本身** —— 所以把一个只剩 1 项
的文件夹里的那 1 项移出去之后，Dock 上会留下一个**空文件夹**：点它只会弹一句
「这个文件夹是空的」（`show_folder_keep_menu` 里那句 `items.is_empty()` 的早退）。

### 现状证据

- `move_out_of_folder`：把子项插到 `fi + 1`（文件夹后面），文件夹原地不动；
- 自检里的实测轨迹就是这个：`「移出文件夹」把它挪到顶层  文件夹里 2 → 1 项` —— 再来一次就是 0 项；
- 用户的实际配置里**确实出现过** 4 个「新建文件夹」，所以这条路径会被走到。

### 两个可选做法

1. **自动解散**（推荐）：移出后如果 `children.is_empty()`，顺手把这个文件夹也删掉 ——
   用户视角是"最后一样东西拿走了，壳子自然没了"，一步到位、不留垃圾；
2. **允许空文件夹**：点它时展开一个空网格 + 一行灰字「这里还没有东西，把图标拖进来」。
   好处是"刚建好还没放东西"这个中间状态也成立（不过右键「新建文件夹」会立刻把当前那一项
   放进去，所以只有"移出"才会空）。

### 风险

- 自动解散会让"特意留一个空文件夹当占位"变得不可能 —— 但现在的模型本来也不支持
  "新建空文件夹"，所以没有回退；
- 若哪天要做**文件夹重命名**，空文件夹保留下来才有意义 —— 这两件事最好一起定。

### 触发条件

用户说"文件夹点开是空的 / 点了没反应"时。

## 附录 A：怎么复现这些数字

**测 CPU 时必须关掉 `DOCK_DEBUG`** —— 它自身的开销比被测对象还大（见 BL-2）。

```powershell
# 前提：Dock 没在运行（单实例互斥锁），且用 danger-full-access 运行
Remove-Item Env:\DOCK_DEBUG -ErrorAction SilentlyContinue
$exe = "app\src-tauri\target\debug\dock-app.exe"
$app = Start-Process -FilePath $exe -PassThru
Start-Sleep -Seconds 15          # 等启动和首轮快节奏结束

$c1 = (Get-Process -Id $app.Id).TotalProcessorTime.TotalMilliseconds
Start-Sleep -Seconds 20          # 采样窗口
$c2 = (Get-Process -Id $app.Id).TotalProcessorTime.TotalMilliseconds

"% 单核 = " + [math]::Round(($c2-$c1)/20/10, 3)
Stop-Process -Id $app.Id -Force
```

**分段计时**：需要临时加计时脚手架 —— 它已经删掉了（见 BL-2「遗留」里的重建步骤）。

**「某条路径占多少 CPU」的做法**：把那条路径的参数改成实质上停用
（例如把 `POLL_IDLE_MS` 改成 60000），再测同一个窗口。差值就是它的净成本。
这一次实验直接把 BL-1 的动机否掉了。**这是最便宜也最有效的归因手段：
不需要任何计时代码，只需要会改一个常量。**优先用它。

**注意**：`DOCK_DEBUG=1` 会打印每个窗口的身份明细（这是排查
「同一应用出现两个图标」的关键手段，**保留在产品代码里**），
但它同时会显著抬高 CPU —— 测 CPU 时必须关掉。

**自动隐藏 A/B**：用 `DOCK_CONFIG_DIR` 指向临时目录（配置只写要改的字段，
其余由 `serde(default)` 补齐）：

```powershell
New-Item -ItemType Directory -Force -Path .dockcfg-ab | Out-Null
'{"autoHide": false}' | Set-Content .dockcfg-ab\config.json -Encoding utf8NoBOM
$env:DOCK_CONFIG_DIR = "$PWD\.dockcfg-ab"
```

**看观感（截图）**：`DOCK_OPENSETTINGS=1` 启动即开设置页；`DOCK_MENUSHOT=<秒>`
打开右键菜单并保持（配 `DOCK_SELFTEST=0`，免得自检先动鼠标）。截屏要注意两点：

1. **必须先 `SetProcessDPIAware()`**，否则 `GetWindowRect` 拿到的是被 DPI 虚拟化过的
   坐标（125% 下会小 0.8 倍），截出来的图会错位；
2. PowerShell 7 里 `Add-Type` 引 `System.Drawing` 会缺一串程序集
   （`System.Drawing.Primitives` → `System.Private.Windows.GdiPlus` → …，追不完）。
   可行做法：只把 **user32 的 P/Invoke** 写成 C# 类，再用
   `Add-Type -AssemblyName System.Drawing.Common` 加载绘图程序集，
   然后直接 `New-Object System.Drawing.Bitmap` / `[System.Drawing.Graphics]::FromImage`。
   流程：枚举窗口拿 Dock 与菜单的矩形 → 取并集 + 30px 边距 → `CopyFromScreen` → 存 PNG。
